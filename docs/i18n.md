# i18n cookbook

vue-i18n in Composition API mode (`legacy: false`). **`en` is the authored source
of truth; `es` is the secondary locale.** Setup lives in
[`app/src/i18n/index.ts`](../app/src/i18n/index.ts).

Strings live in **per-feature TypeScript modules**, not monolithic JSON. Each
module co-locates both locales and types `es` against `en`, so a missing or extra
key in either language is a **compile-time error**, not a runtime warning.

## Structure

```
app/src/i18n/
├── index.ts                 # assembles modules, builds messages, type augmentation
└── locales/
    ├── configs/             # cross-cutting vocab (common)
    ├── components/          # component-scoped strings (shell, missionCard, trophyCase)
    └── pages/               # page/route-scoped strings (onboarding, hub, mission, capture, redeem, about, notFound)
```

The folder split is organizational only. Each module registers under its
**namespace key** (the file name), so keys read `t('hub.title')` regardless of
which folder the file sits in.

## Module format

```ts
// locales/pages/hub.ts
const en = {
  title: 'Your missions',
  empty: 'No missions yet — check back at first pitch.',
}

// Typed against en: a missing or extra key here is a compile error.
const es: typeof en = {
  title: 'Tus misiones',
  empty: 'Aún no hay misiones. Vuelve al primer lanzamiento.',
}

export default { en, es }
```

Because `es` is declared `typeof en`, you literally cannot ship a namespace where
the two locales diverge — TypeScript rejects it before the app boots.

---

## 1. Add a translated string

1. Open the module for that feature (e.g. `locales/pages/hub.ts`).
2. Add the key to **both** `en` and `es` in the same edit. Forget one and `tsc`
   fails on `const es: typeof en`.
3. In the component: `const { t } = useI18n()`, then `t('hub.yourKey')`. Keys
   autocomplete from the schema.

Never use the Options-API `$t`, and never put a hardcoded user-facing string in a
template, a store, or a seed array.

> **Type-safety note:** `en`↔`es` key parity is enforced at compile time, and key
> **autocompletion** works via the `DefineLocaleMessage` augmentation in
> `index.ts`. However, vue-i18n keeps a permissive `t(key: string)` overload, so
> an outright typo in a `t()` call is *not* a `tsc` error — vue-i18n's
> missing-key console warning remains the dev-time backstop for that case.

---

## 2. Add a new namespace

1. Create `locales/<folder>/<name>.ts` exporting `{ en, es }` in the format above.
2. In `index.ts`, import it and add one line to each of the `en` and `es` blocks
   of `messages`.

If a namespace name collides with a JS reserved word (e.g. `import`), alias the
binding — `import importMessages from './locales/pages/import'` — but keep the
registered key unchanged.

---

## 3. Add a new locale

1. For every module, add the new locale alongside `en`/`es`. Diff against `en` to
   be sure everything is translated.
2. Add the code to `SUPPORTED_LOCALES` in `index.ts`, to both `messages` blocks,
   and to `datetimeFormats` / `numberFormats`.
3. Add it to `LocaleSwitcher.vue`'s cycle (it reads `SUPPORTED_LOCALES`, so this
   is usually free).

---

## 4. Translate data, not just UI chrome

Stores and seed data hold message **keys** wherever the content is app-owned.
`stores/missions.ts` seeds `{ id, titleKey, hintKey, color }` — the
component resolves `t(mission.titleKey)`.

The split that matters:

- **App-owned content** (mission titles written by stadium staff in the admin
  tool, badge names, status labels) → translatable, stored as keys or as
  per-locale strings once the admin tool exists.
- **User-generated content** (a fan's nickname, a captured photo) → *not*
  translated. It is data, passed through verbatim.

Enum-style values follow the `t('namespace.enum.' + value)` pattern — see
`hunts.status.*`.

---

## 5. Dates, numbers, currency

Use `d(date, 'short')` and `n(value, 'decimal')` from `useI18n()` — never
hand-format. Timestamps are stored UTC and rendered in the venue's timezone,
which the tenant config supplies.

> Careful with `@` in message strings — vue-i18n treats it as a linked-message
> prefix. Escape it as `{'@'}` inside a message.

---

## The rules

Every user-facing string is a key in a per-feature module, present in both `en`
and `es`. Adding a string means both locales, same commit, enforced by the type
system. Data stays translatable via keys. `LocaleSwitcher.vue` flips the global
locale.
